# 抓猪 2.0 隔离开发与大版本上线方案

> 状态：已确认的开发与发布边界。
>
> 确认日期：2026-08-26。
>
> 当前生产版本：`1.29.1` / Schema `34` / Ruleset `29`。
>
> 目标大版本：`2.0.0`。
>
> 本文只建立隔离开发和发布纪律，不表示 2.0 已经完成或上线。

## 1. 核心决定

抓猪 2.0 的全部新机制、数据迁移、图片和交互改动必须先在独立开发环境完成。开发期间不得把未完成代码、未验收迁移或测试数据放进当前运行中的 MaiBot，也不得让两个正式 Bot 加载 2.0 开发目录。

当前 1.x 版本继续正常运行。只有当 2.0 的全部开发内容完成、全量回归通过、生产数据克隆迁移通过、图片验收通过、故障恢复演练通过，并由用户确认维护时间后，才允许进入一次计划内大维护切换。

## 3. 运行数据隔离

1. 2.0 不得直接打开或迁移当前生产数据库。
2. 需要真实规模数据时，使用 SQLite 在线备份接口生成生产库的一次性克隆，再把克隆放到独立验收目录。
3. 不直接复制运行中的 WAL/SHM 文件，不把开发库放回生产 `data/plugins/local.pig-catcher`。
4. 开发数据库、渲染缓存、临时素材、测试图片和验收报告均使用独立目录，并继续保持 Git 忽略。
5. 开发测试不得连接两个官方群，不得消耗真实玩家额度、猪币、猪猪、美食、道具或效果。
6. 需要完整 MaiBot 加载测试时，使用独立 MaiBot UAT 实例和独立配置；插件 ID 可以保持正式值以验证真实迁移，但不得与生产实例同时位于同一个 MaiBot 插件目录。
7. AppID、AppSecret、管理员 OpenID 和其他密钥不得复制进 2.0 仓库或验收报告。

## 4. 版本与迁移策略

- 2.0 首个正式发布版本使用 `2.0.0`，不再把本轮大型机制合并发布为 `1.30.0`。
- 成就系统当前建议从 Schema `35`、Ruleset `30` 起步；Ruleset `29` 已由 1.x 御厨子五条猪双专属菜规则使用。后续繁育、对战或其他正式确认的机制如需新增持久状态或规则，可在 2.0 开发线继续递增。
- 每个迁移必须支持从当前正式 Schema `34` 的生产克隆直接升级，且可重复执行、可识别已完成状态、失败时不留下半迁移结构。
- 旧玩家资产、余额、图鉴、统计、交易、黑名单、监管审计、群效果和业务回执必须完整保留。
- 管理员发放与系统迁移不得伪造玩家抓猪、做菜、巨物或社交成就。
- 1.x 代码不得直接打开已经升级到 2.0 Schema 的数据库。2.0 回滚依赖维护前完整备份，而不是尝试用旧代码降级新数据库。

## 5. 2.0 开发阶段

### 阶段 A：规则冻结与架构准备

- 汇总社区讨论结果，确认首批 2.0 机制、数值、奖励和公开文案。
- 更新需求追溯、产品规则、领域模型、命令协议、经济概率和视觉规范。
- 明确哪些机制首发，哪些保留为 2.0 后续小版本，不用占位实现冒充完成。
- 建立 Schema 35 迁移、事件增量统计和历史回溯的基础结构。

### 阶段 B：功能闭环开发

每项机制必须按以下顺序完成：

1. 纯规则与领域状态；
2. 数据库迁移、仓储、事务和幂等；
3. 应用服务与既有玩法连接；
4. 明确、低冲突的斜杠命令；
5. 图片渲染、文字降级和长文本适配；
6. 重试、重启、并发和批量行为；
7. 单元、集成和专项 UAT。

任何一个命令只有在解析、授权、事务、渲染、发送、重试、重启和测试全部闭环后才算完成。

### 阶段 C：全量回归与数据迁移演练

- 先合入并保留当前 1.29.1 的全部自动测试和玩法边界，再叠加 2.0 测试。
- 使用最新生产数据库克隆重复执行完整升级。
- 验证四个隔离作用域的模板语义一致、玩家数据互不串群。
- 对全部经济、概率、额度、特殊菜、术式、轮盘、赠送、交易、收藏、监管和管理员流程做回归。
- 重新生成主要图片与完整图鉴，人工检查分页、遮挡、乱码、占位和动画。
- 执行高并发、慢发送、SQLite busy、图片失败、素材缺失、重复消息和插件重启故障注入。
- 执行备份恢复演练，证明可以从维护前快照恢复到 1.x。

### 阶段 D：发布候选冻结

- 功能、数值和迁移冻结为 `2.0.0-rc`。
- RC 阶段只修复缺陷，不继续加入未经讨论的新机制。
- 形成最终变更清单、玩家迁移说明、管理员手册、正式公告和维护窗口方案。
- 用户检查最终验收结果并决定是否批准上线。

## 6. 2.0 上线门禁

同时满足以下条件才允许安排维护：

1. 2.0 全部计划功能完成，没有用占位、文字提示或未接线状态冒充完成。
2. 全量 pytest、Ruff、compileall、锁文件、Manifest、JSON/TOML 和 Git 差异检查通过。
3. 从最新生产克隆执行 Schema 34 到 2.0 最终 Schema 的迁移至少连续成功两次。
4. `PRAGMA quick_check=ok`、外键异常为 0、余额与不可变账本差异为 0。
5. 四作用域数据隔离、专属六星授权和配对菜约束全部通过。
6. 正常抓猪、做菜、吃菜、商城、收藏、批量、赠送、交易、排行、监管和管理命令无回归。
7. 2.0 新机制的所有状态变化均具备事务、幂等、重启恢复和图片结算。
8. 主要页面和特殊事件图全部完成视觉验收，图片失败时文字降级完整。
9. 高峰性能、内存、缓存和本地存储占用达到可接受范围。
10. 完成一次完整升级彩排和一次完整回滚彩排，并保存可审计证据。
11. 用户明确批准上线日期、维护开始时间和公告内容。

## 7. 正式维护切换流程

以下步骤只在用户批准的维护窗口执行，现在不执行：

1. 提前发布维护公告，说明开始时间、预计时长和 1.x 暂停操作范围。
2. 停止正式 MaiBot 接收抓猪插件命令，确认没有活动写事务和未完成交付。
3. 生成最终维护前在线备份，记录文件大小、哈希、Schema、`quick_check`、外键和账本结果。
4. 固化最终 1.x 代码提交或标签，保留可立即恢复的代码与素材版本。
5. 部署已冻结的 2.0.0 代码和正式素材。
6. 对生产数据库执行经过彩排的正式迁移，不运行临时修复脚本或手工 SQL。
7. 执行启动门禁、数据库巡检、素材检查和隔离的管理员烟雾测试。
8. 验证两个 Bot 和四个群作用域均加载 2.0.0 后，再恢复普通玩家命令。
9. 发布 2.0 正式公告并进入重点观察期。

若任何关键门禁失败，立即停止开放，不让玩家继续写入半完成的 2.0 数据库；恢复 1.x 代码、素材和维护前数据库快照，再分析失败原因并重新安排维护。

## 8. 观察与回滚

- 上线后的首个完整抓猪日重点观察错误日志、响应时间、渲染队列、数据库完整性、账本、素材缺失和跨群隔离。
- 2.0 已产生真实新数据后，不能简单把旧代码指向新库。需要回滚时，以维护前快照恢复，维护期间或 2.0 开放后的新业务数据将按事故方案单独处理。
- 维护前备份、2.0 部署包和验收证据放在自动轮转目录之外，未经用户确认不得清理。
