# 领域与数据模型

## 1. 范围键

业务数据统一使用以下范围键：

```text
scope_id = platform + ":" + group_id
player_id = scope_id + ":" + platform_user_id
```

不得使用显示名作为身份键。显示名只保存为快照，用于渲染；用户改名不影响资产归属。

## 2. 核心对象

| 对象 | 说明 | 关键标识 |
| --- | --- | --- |
| 群范围 | 一套独立游戏世界 | `scope_id` |
| 玩家 | 某用户在某群的游戏身份 | `player_id` |
| 猪模板 | 名称、品质、素材和属性范围定义 | `pig_template_id` |
| 猪实例 | 一次抓取产生的独立资产 | `pig_instance_id` |
| 群模板授权 | 将 6 星模板授权给指定群 | `scope_id + pig_template_id` |
| 美食模板 | 名称、品质、食谱倾向、素材和效果定义 | `food_template_id` |
| 美食实例 | 一次做菜产生的独立资产 | `food_instance_id` |
| 图鉴条目 | 玩家曾经获得某模板的事实和统计 | `player_id + template_id` |
| 群纪录 | 某猪模板的最大体型或最大重量 | `scope_id + template_id + record_type` |
| 余额与账本 | 当前猪币及每次变动原因 | `player_id`, `ledger_entry_id` |
| 升级 | 猪饲料和厨具等级 | `player_id + upgrade_type` |
| 道具库存 | 一次性道具持有数量 | `player_id + item_id` |
| 交易报价 | 锁定物品并等待接收方处理 | `trade_id` |
| 展示设置 | 排行榜默认展示的猪和美食 | `player_id` |
| 幂等操作 | 消息与业务结果的唯一映射 | `scope_id + message_id + command_name` |

## 3. 模板与实例分离

模板描述“这种猪或菜是什么”，实例描述“某次实际获得了什么”。

### 3.1 猪模板

计划字段：

- 稳定模板 ID、名称、品质、描述、素材路径和素材校验值
- 公共或群定制范围
- 体型最小值、最大值和分布参数
- 重量最小值、最大值和体型关联参数
- 肥瘦率分布、食谱标签和联动标签
- 启用状态、版本、来源、许可和授权状态

模板 ID 一旦发布不得因改名而变化。素材替换通过模板版本和校验值追踪。

### 3.2 猪实例

计划字段：

- UUID 主键和全库唯一的 8 位展示短编号
- `scope_id`、当前持有者、来源消息、模板版本
- 品质、体型、重量、肥瘦率、官方价值
- 抽取时的概率配置版本与随机结果快照
- 创建时间、锁定状态、处置状态和处置时间

品质和数值快照写入实例，后续调平概率或模板范围不会修改历史资产。

### 3.3 美食实例

计划字段：

- UUID 主键和展示短编号
- 原料猪实例 ID、食谱模板、品质、份量或重量、肥瘦类别
- 官方价值、效果 ID、效果参数快照
- 厨具、消耗品和概率规则版本
- 当前持有者、锁定状态、使用或处置状态

原料关系只用于审计和展示。猪被消耗后保留不可恢复的历史行，不做物理删除。

## 4. 计划数据库表

| 表 | 主要职责 |
| --- | --- |
| `schema_migrations` | 数据库版本和迁移时间 |
| `scopes` | 群范围设置和启用状态 |
| `players` | 用户身份、显示名快照、经验和当前余额缓存 |
| `pig_templates` | 公共与定制猪模板 |
| `scope_pig_templates` | 6 星模板的群授权 |
| `pig_instances` | 猪资产及生命周期 |
| `food_templates` | 美食模板和效果定义 |
| `food_instances` | 美食资产及生命周期 |
| `pig_catalog_entries` | 猪图鉴统计 |
| `food_catalog_entries` | 美食图鉴统计 |
| `group_records` | 最大体型与最大重量纪录 |
| `currency_ledger` | 猪币不可变账本 |
| `upgrades` | 永久升级 |
| `item_inventory` | 消耗品库存 |
| `armed_items` | 已装备、等待下次动作使用的道具 |
| `trade_offers` | 交易报价、锁定和状态 |
| `display_preferences` | 排行展示偏好 |
| `command_receipts` | 幂等命令结果与公示状态 |
| `audit_events` | 管理操作和异常恢复审计 |

余额字段用于快速查询，但每次事务后必须满足：

```text
players.coin_balance == currency_ledger 中该玩家有效变动的总和
```

提供账本重算工具用于验收和故障修复。

## 5. 状态机

### 5.1 资产状态

```text
ACTIVE -> LOCKED_FOR_TRADE -> ACTIVE                 报价拒绝、取消或过期
ACTIVE -> LOCKED_FOR_TRADE -> ACTIVE + OWNER_CHANGED 成交后转移给接收方
ACTIVE -> ACTIVE + OWNER_CHANGED                     赠送后转移给接收方
ACTIVE -> SOLD                                       官方售卖
ACTIVE -> CONSUMED_FOR_COOKING                       猪被做菜
ACTIVE -> CONSUMED                                   美食被使用
```

`OWNER_CHANGED` 是审计事件而不是资产终态。状态变化和持有者变化只能由领域服务执行，任何资产在同一时刻最多被一个有效交易锁定。

### 5.2 交易状态

```text
PENDING -> ACCEPTED
PENDING -> REJECTED
PENDING -> CANCELLED
PENDING -> EXPIRED
```

`ACCEPTED` 是唯一会转移资产和猪币的状态，且转移与状态变更在同一数据库事务中完成。

## 6. 关键不变量

1. 资产只能有一个当前持有者。
2. 非 `ACTIVE` 资产不能重复售卖、赠送、做菜、吃掉或发起新交易。
3. 余额不能小于零，任何扣款都在更新条件中检查余额。
4. 6 星模板只有在当前范围授权且启用时才可抽取。
5. 跨范围的赠送、交易、排行和资产选择一律拒绝。
6. 1 至 5 星猪不可能生成 6 星美食。
7. 6 星猪的出菜品质只能是 5 星或 6 星，概率固定为 90% 和 10%。
8. 图鉴“曾获得”只增不减；重复获得只更新计数与最佳值。
9. 最大体型和最大重量纪录独立更新，数值相同不覆盖更早纪录。
10. 同一命令消息只能产生一个业务收据。
11. 图片生成或发送失败不改变已经提交的业务结果。

## 7. 精确选择规则

同名资产可能有多只，命令不得擅自选择“第一只”。

- 唯一名称：允许直接使用名称。
- 重复名称：返回候选短编号和关键属性，要求使用 `名称#短编号`。
- 模糊匹配：只用于候选提示，不直接执行消耗性动作。
- 短编号冲突：创建时重新生成并由数据库唯一约束兜底；资产转移不改变短编号。

## 8. 事务边界

以下操作必须各自在单个事务中完成：

- 抓猪：限额检查、道具消耗、实例创建、奖励、经验、图鉴、纪录和幂等收据。
- 做菜：原料锁定、道具消耗、猪状态变更、美食创建、奖励、经验、图鉴和收据。
- 官方售卖：所有权检查、资产状态变更、猪币入账和收据。
- 赠送：双方范围检查、所有权转移、图鉴更新和收据。
- 接受交易：报价检查、余额扣增、所有权转移、解锁和收据。
- 吃菜：美食状态变更、效果登记、经验和收据。

渲染在事务提交后进行。发送前通过条件更新把收据从 `PENDING` 领取为 `CLAIMED`，再执行图片或文字发送；重复消息和重启恢复不得重新领取 `CLAIMED` 或 `SENT` 收据。渲染状态和发送状态写回 `command_receipts`，优先保证不重复公示，并允许用户通过查询命令找回极端崩溃窗口中未发出的结果。

## 9. 迁移原则

- SQLite 启用 WAL、外键和忙等待。
- 迁移只前进，不在启动时猜测或破坏未知表。
- 每个迁移有独立版本、事务和测试。
- 破坏性迁移前生成时间戳备份，并保留可验证的恢复说明。
- 运行数据只写入 `self.ctx.paths.data_dir`，临时渲染文件只写入 `self.ctx.paths.runtime_dir`。
