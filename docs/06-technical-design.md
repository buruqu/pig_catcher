# 技术架构设计

## 1. 本机兼容基线

- MaiBot：`1.0.12`
- `maibot-plugin-sdk`：`>=2.7.0,<3.0.0`
- Python：项目兼容目标 `>=3.12`；当前 MaiBot `uv` 运行环境为 `3.14.4`
- 数据库：SQLite，异步访问
- 语言：运行日志、配置面板、命令和用户提示均以简体中文为首要实现

第五轮沿用已验证的 SDK 2.7.x 公共接口和宿主加载器；若后续版本变化，先更新兼容设计再写代码。

当前正式插件为 `1.11.0`，标识为 `schema_version=16`、`asset_manifest_version=4` 和 `ruleset_version=14`。三者独立递增，不能用插件版本代替数据、素材和数值规则版本。本轮只升级资产短编号协议：自动编号从十六进制扩为完整 Base36，管理员可指定 4 至 16 位字母数字，所有查找与唯一约束忽略英文大小写；旧编号内容不重写，素材与概率规则不变。

## 2. SDK 映射

| 需求 | MaiBot 机制 |
| --- | --- |
| 用户显式命令 | `@Command` |
| 插件生命周期 | `MaiBotPlugin` 的加载、卸载和配置更新 |
| 中文配置面板 | `PluginConfigBase`、`Field` 和中文 UI 元数据 |
| 首页管理入口 | `@HomeCard` 声明式按钮，跳转插件配置 |
| 发文字与图片 | `self.ctx.send.text`、`self.ctx.send.image` |
| HTML 转 PNG | `self.ctx.render.html2png` |
| 持久化目录 | `self.ctx.paths.data_dir` |
| 临时渲染目录 | `self.ctx.paths.runtime_dir` |
| 日志 | `self.ctx.logger` |

首版不注册普通消息 `@EventHandler`、LLM `@Tool`、模型提供器或网关。联动猪如果未来需要插件间能力，再基于明确用例设计稳定 `@API`，不提前暴露宽泛写接口。

命令处理器只负责解析、权限、调用服务和发送；随机、价值、交易、纪录和资产状态都留在领域或服务层。
Ruleset 6 将等级、猪饲料和厨具乘数定义为领域层纯函数；抓猪与做菜服务调用它们
结算，渲染适配器调用同一函数生成档案和商城数值，禁止在 HTML 中重新实现概率公式。
结算前数值等级写入随机快照，展示称号不进入快照或概率链路。
Ruleset 7 只把基础每日抓猪额度从 20 次调整为 22 次，不改变冷却、概率、额外次数、
经济或数据库结构。
Ruleset 8 保持六星猪 `90%` 五星、`10%` 六星的品质概率，但六星结果只允许使用
原料猪模板声明的同群对应菜，不再从当前群全部六星菜中随机选取。
Ruleset 9 将抓猪计数改为北京时间四窗口、每窗口 5 次，并把冷却限定在当前有效窗口；
群级手动重置通过审计事件推进有效起点。它同时大幅提高六星菜价值、奖励和三个定制
效果上限，并要求商城显示两种提质消耗品的实际概率。

紧凑列表不会把原始大图直接送入 Runner RPC。渲染器在进程内解码素材，静态图取首帧、
动画取确定性的中间帧，缩放到最长边 256px 后编码为 WebP data URL；单资产卡仍读取原始
媒体并按既有静态或逐帧动画链路输出。HTML 在调用 `render.html2png` 前执行 12 MiB
字节预检，从插件侧为 MaiBot 的 16 MiB RPC 帧保留协议封装余量。

关键规则配置需要交叉校验：

- 概率非负且归一化后总和大于零。
- 等级、价格、次数和期限在合理范围。
- 6 星基础做菜配置必须保持 90/10；只有清单中通过校验的 `next-six-star-cook` 一次性效果可在单次事务中临时调整。
- 黑名单优先于白名单，配置面板明确显示优先级。

## 5. 数据库

- 使用 `aiosqlite` 管理插件自有表，不把自定义模型塞进 MaiBot 核心数据库。
- 数据库默认位于 `ctx.paths.data_dir / "pig_catcher.sqlite3"`，文件名可配置但不能逃逸数据目录。
- 启用 `PRAGMA foreign_keys=ON`、WAL 和合理的 `busy_timeout`。
- 一个数据库连接管理器负责初始化、迁移、事务和关闭。
- 仓储层不提交事务；事务由应用服务统一拥有。
- 迁移文件使用单调版本，测试空库升级和旧版本逐级升级。

Schema 3 为抓取频率、背包、图鉴和群纪录补充查询索引。Schema 4 为食物库存、
食物图鉴、官方售卖和猪币流水补充查询索引。Schema 5 新增稳定玩家统计、资产转移
审计、全群绝对纪录、巨物目击和交易并发索引，并为猪模板增加体型档案。Schema 6
新增 `player_food_effects`，保存一次性效果参数、发放/消费次数和有效期。Schema 7
为 `pig_templates` 新增 `paired_food_template_id`，持久化群专属六星猪的一对一食谱。
Schema 8 新增周与永久抓猪额度加成；Schema 9 新增 `player_restrictions`，Schema 10
把旧的统一社交限制无损拆成永久赠送/收赠黑名单、永久交易黑名单，并保留可到期的
每时段额度上限。Schema 11 为猪模板增加备用图片路径，Schema 12 为猪实例增加
`display_variant`，使同一实例可持久切换立绘与表情包；Schema 13 增加按窗口额度加成，
Schema 14 增加玩家级 `batch_keep_highest` 偏好。Schema 15 通过受检表重建移除余额非负
约束，新增运行时插件黑名单与 `admin-removed` 资产终态；迁移事务提交前执行
`PRAGMA foreign_key_check`，普通经济服务仍通过条件更新禁止透支。
Schema 16 再次只重建猪猪与美食实例表，把 `short_code` 约束改为 4 至 16 位 ASCII
字母数字并使用 `COLLATE NOCASE` 唯一索引。复制语句保留旧编号原始大小写和内容；服务层在
新建时统一大写，并在同一个写事务内跨猪猪、美食检查冲突。
Schema 17 新增 `anti_abuse_cases`、`anti_abuse_case_members`、`anti_abuse_notices`、
`anti_abuse_holds` 和 `anti_abuse_events`。自动限制不复用永久 `player_restrictions`，因此到期、
人工解除和永久黑名单不会互相覆盖。历史 `asset_transfer_events` 沿用 Schema 5 的范围时间索引，
不改表也不重写历史行。

### 自动监管事务

`RegulationService` 在赠送或接受交易的现有显式事务中读取滚动流转图，并把当前拟议流转作为
锚点分析。资产信号沿猪实例及美食 `source_pig_instance_id` 归并血缘；已接受交易同时保留价格
与官方价值，明显高价时建立买方到卖方的猪币收益方向。纯正常价格交易可以作为图谱上下文，
但不能在没有赠送或价格偏离时单独触发处罚。

判定顺序固定为：人工永久限制检查 → 自动到期处理 → 当前临时限制检查 → 图谱分析 →
案件与提醒/限制写入 → 允许时再扣款和转移。首次提醒生成 `PENDING` 通知，事务提交后由群消息
发送器领取；只有平台确认发送成功并写为 `SENT`，成员的 `warning_served_at` 才会设置。
后续重复消息先命中业务回执，不会再次增加监管事件。配置管理员只留证据和提醒，不写自动限制。

群消息只消费预先生成的中性 `message_text`。内部 `score`、阈值和 `evidence_json` 不进入普通
回执、管理群回复或图片模型；管理员群命令只显示案件号、状态、相关账号和当前到期限制。

一次成功抓取在同一事务中
写入实例、奖励账本、余额、经验、图鉴、两类品种纪录、两类全群绝对纪录、巨物目击、稳定统计、额外次数、美食效果、道具消耗和命令回执；任一步骤
失败都会整体回滚。

一次成功做菜在同一事务中消耗原料猪、生成一份或两份美食、写做菜奖励、经验、
图鉴、美食效果、道具消耗与命令回执。购买、升级、食用和单项/批量官方售卖同样在单一事务中更新资产、库存、
经验、不可变账本、缓存余额与收据。渲染和发送始终发生在事务提交之后。

赠送在一个事务中转移所有权、更新双方稳定统计、写转移审计与收据。接受交易在一个事务中
重新校验角色、范围、状态、有效期、资产锁和余额，再写两条零和账本分录、转移资产、完成报价、
更新双方统计与收据。余额不足不改变待处理报价。

处罚工具先执行 SQLite 在线备份，再按精确 `scope_id + platform_user_id` 解析玩家。
三类限制、相关待处理报价取消/解锁和审计事件在一个事务中提交；任一玩家不属于目标群时整批拒绝。

群内 `AdministrationService` 只接受配置管理员入口：单人/全员猪币调整逐玩家写账本；资产
发放复用已授权模板与全库短编号校验；资产删除保留历史并修复失效纪录；三类运行时黑名单
和个人额度重置都按当前 `scope_id` 精确处理。每条改变状态的猪管命令把业务、审计与消息
回执放在同一事务中，重复消息不会重复发币、扣币、生成资产或重置额度。

面板的额度、黑名单和公告开关由同一生命周期处理器读取。处理器先一次性清除所有已领取
开关，再分别执行服务，保证配置热更新或重启不会重复产生副作用。公告按目标范围读取最近
`stream_id`，先写 `announcement-send-claimed`，调用 SDK 发送后再写成功或失败审计；失败
不自动重试。QQ 官方网关是否允许发送仍由主动消息权限或五分钟被动回复上下文决定。

### 5.1 并发

- 同一玩家的改变状态命令使用进程内异步锁串行化。
- 交易同时按稳定顺序锁定双方，避免死锁。
- 数据库唯一键和条件更新作为最终防线，不能只相信进程内锁。
- 重启后锁由数据库资产状态恢复，不依赖内存。

### 5.2 幂等

幂等键优先使用平台提供的消息 ID；若适配器缺少消息 ID，使用经过审计的稳定事件键，不用当前时间生成。

`command_receipts` 至少保存：

- 幂等键、命令、玩家、群范围
- 业务结果类型和业务对象 ID
- 文字摘要
- 渲染状态、图片校验值和发送状态
- 创建与最后更新时间

业务事务写入 `COMMITTED` 收据。重复事件查询到收据后不得重新执行领域服务。

发送状态采用 `PENDING -> CLAIMED -> SENT`，失败可记录为 `FAILED`。发送器先用条件更新领取一次发送权，再调用平台接口；进程若在平台已接收但状态尚未写成 `SENT` 时崩溃，重启后不自动重发 `CLAIMED` 收据，以牺牲极小概率的自动公示来保证不重复公示。用户仍可通过背包、详情或交易查询取得已提交结果。

## 6. 随机与规则版本

- 随机源通过接口注入，生产使用系统安全随机源，测试使用固定序列。
- 概率计算函数是纯函数，输入权重、升级、道具和资格，输出归一化权重与解释。
- 属性生成、价值、做菜品质和经验升级都使用纯函数并携带 `ruleset_version`。
- 每次结算把规则版本与关键输入写入实例或收据，方便复算。

## 7. 渲染管线

静态输出使用本地 HTML/CSS 模板和 `ctx.render.html2png()`：

1. 领域对象转换为无副作用的视图模型。
2. 对所有用户文本转义并限制长度。
3. 只引用插件资产和 `data_dir` 中当前群已授权素材。
4. 生成固定宽度、受限高度的 HTML。
5. SDK 返回 Base64 PNG 后，检查格式、解码、尺寸、文件大小和透明像素。
6. 调用 `ctx.send.image`。
7. 成功后清理临时文件；失败则记录并发送文字摘要。

渲染器不访问互联网。模板样式和素材加载必须在离线环境可用。

动画输出先由 Chromium 生成不含素材的静态卡片底图，再逐帧把原始 GIF 或动画 WebP 合成到固定媒体槽中。合成器保留有效帧时长、循环和帧数；原素材缺少显式帧时长时使用配置回退值。为防止编码器把连续相同画面合并，输出帧带有不可感知的单像素交替标记。原始素材始终按字节保存，不在导入或渲染前重编码。

第三轮提供抓取/详情单猪卡、档案、背包、图鉴、群纪录和道具回执模板。第四轮新增
美食详情、背包、图鉴、商城、账本和经济回执模板。第五轮新增 `NEW`、体型评价、全群巨物、
赠送/交易票据、交易列表、展示位和原创白粉排行榜。版本 1.2.0 在背包、图鉴和
排行榜中把动画素材的确定性中间帧转为内存 PNG 预览并显示动态标记；单资产视图仍
执行完整逐帧合成，原始文件不改写。

## 8. 素材导入

素材导入协议分为两个路径：

- 1 至 5 星公共素材：由版本化定义生成导入包，通过同一清单协议导入。
- 6 星群素材：落入本机暂存区，验证清单、图片、所属群和授权后再原子激活，不进入公共 Git 历史。

Asset Manifest v4 在 v3 的媒体、授权、`effect_id` 和 `effect_params` 上增加
`paired_food_template_id`，并校验六星猪和六星菜同群、一对一且完整覆盖。验证器按
文件内容而不是扩展名识别 PNG、JPEG、WebP 和 GIF，完整
解码所有帧并保存格式、动画、帧数、时长、循环和透明度元数据。文件路径通过解析后
的根目录校验，拒绝绝对路径、`..`、符号链接逃逸和无法识别的媒体。停用模板不删除历史行。

## 9. 安全与隐私

- 不记录 QQ 账号密码、Token、Cookie 或素材原始私密链接。
- 日志中的用户 ID 默认脱敏，调试级别也不输出完整交易对象。
- 6 星素材只在所属群渲染和查询。
- 管理操作写审计事件，包含操作者、范围、动作和结果。
- SQL 全部参数化。
- 资产描述只来自经过审核的静态数据，不把群聊文本拼成 HTML。

## 10. 可观测性与恢复

日志事件至少覆盖：

- 插件加载、数据库版本和素材统计
- 概率配置校验
- 抓取、做菜、售卖、赠送和交易的收据 ID
- 渲染与发送失败
- 账本不一致、资产状态冲突和迁移失败

维护任务支持：

- SQLite 一致性检查
- 数据库在线备份与保留数量清理
- 过期素材暂存目录清理
- 过期交易报价解锁
- 全库玩家缓存余额与不可变流水合计对账
- 当前启用素材文件存在性巡检

批量资产安全规则集中在 `infrastructure/repositories/batch_safety.py`：普通资产使用

Ruleset 13 把概率处理拆成普通叠加层与六星菜独占层。普通抓猪最多同时使用一个概率菜、
一个体型菜和一个装备道具；普通做菜最多同时使用一个概率菜和一个装备道具，明确允许
“一猪六吃”与超级主厨香料叠加并统一封顶。若存在与当前动作兼容的六星菜效果，服务层
直接从未应用等级、升级、属性、道具和其他菜品的纯基础权重开始结算；所有被跳过资源
保持原状，结果模型、幂等回执和渲染卡片共同记录独占来源及最终概率。

Ruleset 14 在普通叠加层内增加两个纯函数边界：`apply_monotonic_high_rarity_multipliers`
先计算相对权重候选，再把任何可能下降的 4/5/6 星档位固定在加成前，新增份额只由 1 至
3 星供资；`lift_target_rarity_from_lower` 按旧倍率校准目标概率，但只从严格更低星级转移。
抓猪概率道具先建立公开基准，再进入等级/饲料成长层。该顺序与最终权重一起写入随机快照，
避免 UI 公示、抽取逻辑和组合效果出现三套口径。六星菜独占层完全不变。
