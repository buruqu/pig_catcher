# 技术架构设计

## 1. 本机兼容基线

- MaiBot：`1.0.12`
- `maibot-plugin-sdk`：`>=2.7.0,<3.0.0`
- Python：项目兼容目标 `>=3.12`；当前 MaiBot `uv` 运行环境为 `3.14.4`
- 数据库：SQLite，异步访问
- 语言：运行日志、配置面板、命令和用户提示均以简体中文为首要实现

第五轮沿用已验证的 SDK 2.7.x 公共接口和宿主加载器；若后续版本变化，先更新兼容设计再写代码。

当前正式插件为 `1.27.0`，标识为 `schema_version=33`、`asset_manifest_version=4` 和
`ruleset_version=27`。三者独立递增，不能用插件版本代替数据、素材和数值规则版本。
Schema 18 为抓猪收据增加普通额度成本，Ruleset 16 增加六星菜专属抓猪、滚动七天到期、
多次六星效果与普通六星做菜平衡；Schema 19 修复存量“一猪六吃”效果类型与新参数不匹配；
Schema 20 与 Ruleset 17 同步 9 道公共四/五星菜的新效果、现有可用实例和未消费队列；
Schema 21 收敛热加载期间可能先落库的“猪利猪”早期参数；Schema 22 增加群级六星菜
时效和按玩家独立用量，并升级糖醋排骨、猪鼻蛋包饭存量快照；Schema 23 收敛猪鼻蛋包饭
复合效果、糖醋排骨隐藏参数和两道十连菜的小保底；Schema 24 为装备道具增加连续使用
剩余次数，并增加玩家级最后一份美食 30 秒确认状态；Schema 25 将耗尽状态统一表示为
队列记录不存在；Schema 26 保存六星菜永久进度，Schema 27 允许系统群效果资产赠送，
Schema 28 把猪鼻蛋包饭改为每玩家一次额外抓猪；Schema 29 将阿萨姆红茶奶雾锅的
自动赠送概率同步到新模板、现有可用/交易锁定菜品和未过期群效果；Schema 30 为抓猪额度
统计增加 `player_id + command_name + created_at + catch_quota_cost` 覆盖索引；Schema 31 为
猪猪和美食实例增加持久收藏标记及活动收藏查询索引，历史实例默认未收藏；Schema 32 增加
玩家术式资格、精确群运行中术式和苍赫组合进度；Schema 33 增加持久轮盘状态、允许同一道
来源菜生成多个奖励效果，并收敛六道重做菜的模板、实例和未消费效果；Manifest 协议保持不变。

## 2. SDK 映射

| 需求 | MaiBot 机制 |
| --- | --- |
| 用户显式命令 | `@Command` |
| 插件生命周期 | `MaiBotPlugin` 的加载、卸载和配置更新 |
| 中文配置面板 | `PluginConfigBase`、`Field` 和中文 UI 元数据 |
| 首页管理入口 | `@HomeCard` 声明式按钮，跳转插件配置 |
| 发文字与图片 | `self.ctx.send.text`、`self.ctx.send.image` |
| HTML 转 PNG | `self.ctx.render.html2png` |
| 当前群近期消息元数据 | `self.ctx.message.get_by_time_in_chat`，只计发送者、时间和命令过滤结果 |
| 持久化目录 | `self.ctx.paths.data_dir` |
| 临时渲染目录 | `self.ctx.paths.runtime_dir` |
| 日志 | `self.ctx.logger` |

插件不注册普通消息 `@EventHandler`、LLM `@Tool`、模型提供器或网关。监管只在赠送/接受交易
命令执行时按需查询当前群近期消息，不监听、保存或分析聊天正文。

命令处理器只负责解析、权限、调用服务和发送；随机、价值、交易、纪录和资产状态都留在领域或服务层。
`/今日巨物` 直接以 `pig_instances + command_receipts` 的真实抓猪来源做只读窗口查询，
使用 SQLite `ROW_NUMBER()` 在当前作用域和北京时间当日内分别选出每位玩家的体型、重量最佳实例；
因此无需新增表或迁移，也不会把管理员发放资产、其他群资产或当前持有人误认为原抓取者。
Ruleset 6 将等级、猪饲料和厨具乘数定义为领域层纯函数；抓猪与做菜服务调用它们
结算，渲染适配器调用同一函数生成档案和商城数值，禁止在 HTML 中重新实现概率公式。
结算前数值等级写入随机快照，展示称号不进入快照或概率链路。
Ruleset 7 只把基础每日抓猪额度从 20 次调整为 22 次，不改变冷却、概率、额外次数、
经济或数据库结构。
Ruleset 8 保持六星猪 `90%` 五星、`10%` 六星的品质概率，但六星结果只允许使用
原料猪模板声明的同群对应菜，不再从当前群全部六星菜中随机选取。
Ruleset 9 将抓猪计数改为北京时间四窗口、每窗口 5 次，并把冷却限定在当前有效窗口；
群级手动重置通过审计事件推进有效起点。它同时大幅提高六星菜价值、奖励和三个定制
效果上限，并要求商城显示两种提质消耗品的实际概率。

紧凑列表不会把原始大图直接送入 Runner RPC。渲染器在线程池中解码素材，静态图取首帧、
动画取确定性的中间帧，缩放到最长边 256px 后编码为 WebP data URL；单资产静态卡也只传
最长边 768px、质量 90 的瞬时 WebP，原文件保持逐字节不变。衍生预览以路径、大小、修改时间、
尺寸和缓存协议组成稳定键，使用 8 MiB 进程内 LRU 与 64 MiB 数据目录磁盘缓存，并对同键
并发请求执行单飞。HTML 在调用 `render.html2png` 前执行 12 MiB 字节预检，从插件侧为
MaiBot 的 16 MiB RPC 帧保留协议封装余量。

## 5. 数据库

- 使用 `aiosqlite` 管理插件自有表，不把自定义模型塞进 MaiBot 核心数据库。
- 数据库默认位于 `ctx.paths.data_dir / "pig_catcher.sqlite3"`，文件名可配置但不能逃逸数据目录。
- 启用 `PRAGMA foreign_keys=ON`、WAL 和合理的 `busy_timeout`。
- 一个数据库连接管理器负责初始化、迁移、事务和关闭。
- 写事务使用单一进程锁和 `BEGIN IMMEDIATE` 串行化；只读事务使用最多 4 个短连接并发，
  强制 `PRAGMA query_only=ON`，关闭生命周期会等待全部活动读取结束。
- 仓储层不提交事务；事务由应用服务统一拥有。
- 迁移文件使用单调版本，测试空库升级和旧版本逐级升级。

Schema 3 为抓取频率、背包、图鉴和群纪录补充查询索引。Schema 4 为食物库存、
食物图鉴、官方售卖和猪币流水补充查询索引。Schema 5 新增稳定玩家统计、资产转移
审计、全群绝对纪录、巨物目击和交易并发索引，并为猪模板增加体型档案。Schema 6
新增 `player_food_effects`，保存一次性效果参数、发放/消费次数和有效期。Schema 7
为 `pig_templates` 新增 `paired_food_template_id`，持久化群专属六星猪的一对一食谱。
Schema 8 新增周与永久抓猪额度加成；Schema 9 新增 `player_restrictions`，Schema 10
把旧的统一社交限制无损拆成永久赠送/收赠黑名单、永久交易黑名单，并保留可到期的
每时段额度上限。Schema 11 为猪模板增加备用图片路径，Schema 12 为猪实例增加
`display_variant`，使同一实例可持久切换立绘与表情包；Schema 13 增加按窗口额度加成，
Schema 14 增加玩家级 `batch_keep_highest` 偏好。Schema 15 通过受检表重建移除余额非负
约束，新增运行时插件黑名单与 `admin-removed` 资产终态；迁移事务提交前执行
`PRAGMA foreign_key_check`，普通经济服务仍通过条件更新禁止透支。
Schema 16 再次只重建猪猪与美食实例表，把 `short_code` 约束改为 4 至 16 位 ASCII
字母数字并使用 `COLLATE NOCASE` 唯一索引。复制语句保留旧编号原始大小写和内容；服务层在
新建时统一大写，并在同一个写事务内跨猪猪、美食检查冲突。
Schema 17 新增 `anti_abuse_cases`、`anti_abuse_case_members`、`anti_abuse_notices`、
`anti_abuse_holds` 和 `anti_abuse_events`。自动限制不复用永久 `player_restrictions`，因此到期、
人工解除和永久黑名单不会互相覆盖。历史 `asset_transfer_events` 沿用 Schema 5 的范围时间索引，
不改表也不重写历史行。

### 自动监管事务

`RegulationService` 在赠送或接受交易的现有显式事务中读取滚动流转图，并把当前拟议流转作为
锚点分析。资产信号沿猪实例及美食 `source_pig_instance_id` 归并血缘；已接受交易同时保留价格
与官方价值，明显高价时建立买方到卖方的猪币收益方向。纯正常价格交易可以作为图谱上下文，
但不能在没有赠送或价格偏离时单独触发处罚。

事务开始前，`plugin.py` 通过公共 `message.get_by_time_in_chat` 能力最多读取当前精确聊天流
最近 5,000 条、30 天内的非命令消息。服务只聚合每名发送者的消息数和活跃日期，并使用
5 分钟内存缓存；正文、二进制内容和消息列表都不进入数据库。双方均达到 30 条/7 日且存在
双向赠送时，相关赠送事件才从本轮图排除。消息不超过 5 条/2 日、插件账号不满 7 天且玩法
动作不超过 10 次者进入疑似小号严格来源集合；查询失败时层级为 `unknown`，不做身份猜测。

判定顺序固定为：人工永久限制检查 → 解析配置管理员并排除其当前身份 → 监管单 24 小时到期处理 →
非管理员当前临时限制检查 → 排除管理员历史流转 → 图谱分析 →
案件与提醒/限制写入 → 允许时再扣款和转移。首次提醒生成 `PENDING` 通知，事务提交后由群消息
发送器领取；只有平台确认发送成功并写为 `SENT`，成员的 `warning_served_at` 才会设置。
后续重复消息先命中业务回执，不会再次增加监管事件。配置管理员完全不生成案件、评分、提醒、
限制或监管事件；管理员参与的历史流转也不进入后续图，但非管理员已有的活动限制仍优先阻断。

监管单的硬到期点固定为 `created_at + 24h`，后续证据只更新 `updated_at`，不得延长生命周期。
任何监管入口在读取限制、领取通知或列案前先惰性执行到期：案件改为 `dismissed`、分数和成员
累计归零、未发送通知失效、活动限制释放，并追加 `automatic-expiry` 历史事件。列表和案件详情
只查询未撤销且创建未满 24 小时的记录，因此不存在“界面消失但限制仍生效”的隐形处罚。

监管恢复使用 `tools/reset_regulation_state.py`。默认只读预览；`--execute` 先调用 SQLite 在线
备份 API，再在一个 `BEGIN IMMEDIATE` 事务中撤销案件、清零当前分数/成员累计、失效未投递通知
并释放限制。留空 `--scope-id` 时全局处理，每案追加 `global-reset` 事件并按涉及作用域追加
`automatic-regulation-bulk-reset` 通用审计；提供精确 `platform:group_id` 时只处理该群，改写为
`scope-reset` 事件与 `automatic-regulation-scope-reset` 管理审计。旧事件和已发送通知不删除。

群消息只消费预先生成的中性 `message_text`。内部 `score`、阈值和 `evidence_json` 不进入普通
回执、管理群回复或图片模型；管理员群命令只显示案件号、状态、相关账号和当前到期限制。

一次成功抓取在同一事务中
写入实例、奖励账本、余额、经验、图鉴、两类品种纪录、两类全群绝对纪录、巨物目击、稳定统计、额外次数、美食效果、道具消耗和命令回执；任一步骤
失败都会整体回滚。

一次成功做菜在同一事务中消耗原料猪、生成一份或两份美食、写做菜奖励、经验、
图鉴、美食效果、道具消耗与命令回执。购买、升级、食用和单项/批量官方售卖同样在单一事务中更新资产、库存、
经验、不可变账本、缓存余额与收据。渲染和发送始终发生在事务提交之后。

糖醋排骨食用、云海锅食用和糖醋排骨机会重置均直接把完整全群事件文字写入原业务回执。
事务提交后，命令适配器使用同一 `PENDING -> CLAIMED -> SENT/FAILED` 发送权渲染大事件图；
不创建第二条公告回执，也不调用主动消息或 `@全体成员` 接口。资格获取与真正重置是两笔
独立业务、两条独立消息回执，因此可以各自公示一次，同时不会把任一动作重复发送。

赠送在一个事务中转移所有权、更新双方稳定统计、写转移审计与收据。接受交易在一个事务中
重新校验角色、范围、状态、有效期、资产锁和余额，再写两条零和账本分录、转移资产、完成报价、
更新双方统计与收据。余额不足不改变待处理报价。

处罚工具先执行 SQLite 在线备份，再按精确 `scope_id + platform_user_id` 解析玩家。
三类限制、相关待处理报价取消/解锁和审计事件在一个事务中提交；任一玩家不属于目标群时整批拒绝。

群内 `AdministrationService` 只接受配置管理员入口：单人/全员猪币调整逐玩家写账本；资产
发放复用已授权模板与全库短编号校验；资产删除保留历史并修复失效纪录；三类运行时黑名单
和个人额度重置都按当前 `scope_id` 精确处理。每条改变状态的猪管命令把业务、审计与消息
回执放在同一事务中，重复消息不会重复发币、扣币、生成资产或重置额度。

面板的额度、黑名单和公告开关由同一生命周期处理器读取。处理器先一次性清除所有已领取
开关，再分别执行服务，保证配置热更新或重启不会重复产生副作用。公告按目标范围读取最近
`stream_id`，先写 `announcement-send-claimed`，调用 SDK 发送后再写成功或失败审计；失败
不自动重试。QQ 官方网关是否允许发送仍由主动消息权限或五分钟被动回复上下文决定。

### 5.1 并发

- 同一玩家的改变状态命令使用进程内异步锁串行化。
- 交易同时按稳定顺序锁定双方，避免死锁。
- 数据库唯一键和条件更新作为最终防线，不能只相信进程内锁。
- 重启后锁由数据库资产状态恢复，不依赖内存。
- 在线备份只使用独立备份锁，不占普通业务事务锁；备份先落到目标同目录临时文件，
  `quick_check=ok` 后才原子替换最终文件。卸载按备份锁、业务锁的固定顺序等待。

### 5.2 幂等

幂等键优先使用平台提供的消息 ID；若适配器缺少消息 ID，使用经过审计的稳定事件键，不用当前时间生成。

`command_receipts` 至少保存：

- 幂等键、命令、玩家、群范围
- 业务结果类型和业务对象 ID
- 文字摘要
- 渲染状态、图片校验值和发送状态
- 创建与最后更新时间

业务事务写入 `COMMITTED` 收据。重复事件查询到收据后不得重新执行领域服务。

发送状态采用 `PENDING -> CLAIMED -> SENT`，失败可记录为 `FAILED`。发送器先用条件更新领取一次发送权，再调用平台接口；进程若在平台已接收但状态尚未写成 `SENT` 时崩溃，重启后不自动重发 `CLAIMED` 收据，以牺牲极小概率的自动公示来保证不重复公示。用户仍可通过背包、详情或交易查询取得已提交结果。

## 6. 随机与规则版本

- 随机源通过接口注入，生产使用系统安全随机源，测试使用固定序列。
- 概率计算函数是纯函数，输入权重、升级、道具和资格，输出归一化权重与解释。
- 属性生成、价值、做菜品质和经验升级都使用纯函数并携带 `ruleset_version`。
- 每次结算把规则版本与关键输入写入实例或收据，方便复算。

## 7. 渲染管线

静态输出使用本地 HTML/CSS 模板和 `ctx.render.html2png()`：

1. 领域对象转换为无副作用的视图模型。
2. 对所有用户文本转义并限制长度。
3. 只引用插件资产和 `data_dir` 中当前群已授权素材。
4. 生成固定宽度、受限高度的 HTML。
5. SDK 返回 Base64 PNG 后，在线程池检查格式、解码、尺寸、文件大小和透明像素。
6. 在插件级并发名额内调用 `ctx.send.image`；默认同时最多 2 个图片任务。
7. 候场超过 5 秒、渲染失败或发送失败时记录分阶段耗时并发送文字摘要。

渲染器不访问互联网。模板样式和素材加载必须在离线环境可用。

动画输出先由 Chromium 生成不含素材的静态卡片底图，再逐帧把原始 GIF 或动画 WebP 合成到固定媒体槽中。合成器保留有效帧时长、循环和帧数；原素材缺少显式帧时长时使用配置回退值。合成后的待编码帧立即量化为调色板图，动画任务默认串行，并在建立整卡帧列表前按帧数、画布和最大 GIF 缓冲估算 256 MiB 工作内存预算；写出后关闭帧与缓冲，再按实际 GIF 大小复核 Base64 峰值。为防止编码器把连续相同画面合并，输出帧带有不可感知的单像素交替标记。原始素材始终按字节保存，不在导入或渲染前重编码。

第三轮提供抓取/详情单猪卡、档案、背包、图鉴、群纪录和道具回执模板。第四轮新增

## 10. 可观测性与恢复

日志事件至少覆盖：

- 插件加载、数据库版本和素材统计

- 抓取、做菜、售卖、赠送和交易的收据 ID

维护任务支持：

- SQLite 一致性检查
- 数据库在线备份与所有插件备份族的统一保留数量清理
- 过期素材暂存目录清理
- 仅在生产库全部模板和全部保留备份均不再引用时清理旧不可变素材目录，并额外保留最新回退版
- 过期交易报价解锁

- 当前全部模板素材文件存在性巡检

余额与不可变账本对账已在第四轮实现；第五轮补齐过期报价解锁。版本 1.24.0 首次维护默认
延迟 120 秒，轻量过期清理仍按小时执行，`quick_check` 和全账本对账默认每 24 小时一次；
在线备份使用独立锁，不再占用普通命令的全局事务锁。未知异常只记录日志，不自动篡改余额、
库存或业务历史。

运行 `backups/` 下所有直接普通 `*.sqlite3` 共享统一保留数量。旧 catalog 清理前读取当前
全部猪/菜模板（包括禁用模板的历史实例）和每份保留备份中的素材引用；任一保留备份无法
打开或缺少所需表时，本轮素材清理 fail-closed，不能以“无法证明仍引用”代替“已确认无引用”。
备份扫描完成后会再次读取活动模板；新发布 catalog 默认需度过 24 小时保护期才进入删除候选，
以隔离外部导入与后台维护的并发窗口。需要永久保留的发布保护点必须放到运行备份目录之外。

这些工具默认只读或需要显式确认，不在插件启动时静默修复未知问题。

Ruleset 13 把概率处理拆成普通叠加层与六星菜独占层。普通抓猪最多同时使用一个概率菜、
一个体型菜和一个装备道具；普通做菜最多同时使用一个概率菜和一个装备道具，明确允许

直接从未应用等级、升级、属性、道具和其他菜品的纯基础权重开始结算；所有被跳过资源
保持原状，结果模型、幂等回执和渲染卡片共同记录独占来源及最终概率。

Ruleset 14 在普通叠加层内增加两个纯函数边界：`apply_monotonic_high_rarity_multipliers`
先计算相对权重候选，再把任何可能下降的 4/5/6 星档位固定在加成前，新增份额只由 1 至
3 星供资；`lift_target_rarity_from_lower` 按旧倍率校准目标概率，但只从严格更低星级转移。
抓猪概率道具先建立公开基准，再进入等级/饲料成长层。该顺序与最终权重一起写入随机快照，
避免 UI 公示、抽取逻辑和组合效果出现三套口径。六星菜独占层完全不变。

Ruleset 15 增加自动资产流向监管，不改变抓猪与做菜数值。Ruleset 16 将实际选中的六星
抓猪效果映射为专属次数：`command_receipts.catch_quota_cost` 对普通抓猪写 `1`、专属抓猪
写 `0`，仓储同时返回普通额度计数、全部成功计数和最后成功时间。普通额度门只使用前者，
冷却和违规处罚硬上限使用后两者，因此专属次数既不会占用普通额度，也不能绕过处罚。
多次数效果仍按 FIFO 和独占组选择，只有成功事务才递增 `consumed_uses`。

Ruleset 17 在普通效果层增加四个边界。第一，固定百分点的五星/六星抓猪增益通过
`_lift_five_and_six_by_points` 只从 1 至 3 星池供资，保证四星和未指定高星不下降。
第二，联动定向效果先把候选模板限制为当前作用域带联动集合的启用模板，再使用
`15/55/30` 的 3/4/5 星固定分布；概率资源被排除但不消费。第三，巨物五星复合效果在
品质结算后仅对五星候选模板追加巨物档案权重，不反向改变品质。第四，做菜结算支持最多
5 条猪饺队列与“一猪六吃”、超级主厨香料一起累加，统一封顶 50%；猪咪莓蛋糕则通过
五星概率下限函数为 1 至 5 星原料建立至少 85% 的五星结果，六星原料保持等待。

Schema 20 对正式模板、`ACTIVE/LOCKED` 美食实例和未消费效果队列做可重复的参数迁移。
迁移以正式菜名精确匹配，不做模糊匹配；已经消费完成或进入历史终态的数据保持原快照。
Schema 21 按“猪利猪”正式显示名修正模板、可用实例与未消费队列，用于兼容开发热加载

`display_name`：前者只写入结构化随机快照与幂等回执供审计，后者才进入实际选中效果的

神龙化猪七星云海锅优先进入纯基础独占分支；个人效果和装备道具保持未消费。普通群效果

Ruleset 19 不迁移历史资产。`CatchQuotaLayers` 统一基础、永久、滚动七天、当前时段、今日时段
